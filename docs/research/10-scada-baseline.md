# 10 The SCADA baseline, and where DurianDB stands

Written 2026-10-20 after a course correction. The table below was re-verified against the tree on 2026-10-27. The project had drifted toward generic web-application polish (migrations, notifications, session screens). The first goal was a reference for how a **SCADA** system works, so the roadmap should follow the functions a SCADA system is expected to have, not the order in which ideas came up.

Sources and honesty: the function list below is the commonly accepted breakdown of a SCADA system (field connectivity, tag database, historian, alarm management, HMI, control, security and audit, reporting, calculation, resilience, integration). The alarm material follows the ISA-18.2 alarm state model and the EEMUA 191 alarm-rate guidance as described by secondary sources and vendor documentation (the standards themselves are paywalled and were not read): [ICONICS alarm state diagram](https://documentation.iconics.com/v10.97.3/Content/Alarming/Alarm%20Server/Alarm%20References/alarm-state-transition-diagram.htm), [WinCC OA alarm shelving](https://www.winccoa.com/documentation/WinCCOA/latest/en_US/alarmshelving/topics/alarm_shelving_overview.html), [Emerson alarm management paper](https://d1-live.emerson.com/documents/automation/article-alarm-management-by-numbers-deltav-en-38292.pdf). Treat figures as guidance. ISA-101 (HMI) and IEC 62443 (security) are named as the relevant families but were not researched in detail.

## Baseline against DurianDB

| # | Function | Expected of a SCADA | DurianDB today | Gap |
|---|---|---|---|---|
| 1 | Field connectivity | Drivers for common protocols, comms health, reconnect | Modbus TCP/RTU/ASCII, MQTT over TLS, HTTP JSON poll, SQL, virtual, and HTTP ingest push with scoped tokens (`durian/ingest.py`). Health per source, back-off. | OPC UA, SNMP, BACnet, DNP3 |
| 2 | Tag database | Name, description, engineering units, range, type, scaling, source and address, scan class | Name, description, unit, engineering range, tags, binary and multistate labels, scaling in drivers, logging mode and tolerance, calculated points | Scan classes |
| 3 | **Data quality and time** | Every value carries a quality (good, uncertain, bad, stale) and a source timestamp apart from the server's | GOOD, UNCERTAIN and BAD quality and a source timestamp per value, with future-clock, stale and out-of-order rules (`durian/core.py`, `durian/ingest.py`) | None |
| 4 | **Alarm management** | ISA-18.2 states: normal, unacknowledged, acknowledged, return-to-normal unacknowledged, plus shelved, suppressed by design, out of service. Priorities, deadband or hysteresis, delays, chatter protection, rate KPIs | Raise, clear and acknowledge; 7 levels; explicit ISA-18.2 states; deadband, on-delay and off-delay; shelving with reason and expiry; suppression; out of service; maintenance windows; journal; KPIs; escalation | None |
| 5 | Historian | Long-term store, retention, rollups, export, no silent loss | SQLite or MariaDB, rollups, retention, backups, CSV, buffered writes with an alarm on failure | Compression beyond tolerance, backfill, store and forward at the edge |
| 6 | HMI | Process graphics bound to live tags, navigation, alarm indication, trends, faceplates | Dashboards with value, gauge, chart, alarms, table, setpoint, text, status, mimic and prediction widgets; a point page with trend, logbook and operator notes; history with comparison | None |
| 7 | Control actions | Permissioned writes, audit, limits on what can be sent, confirmation | Set with roles and audit; engineering limits, a per-write maximum step, two-step confirmation and a required reason (`durian/app.py`) | Time-based rate limits |
| 8 | Security and audit | Least privilege, authentication, session control, full change audit with before and after, secure transport, account lifecycle | Roles, lockout, CSRF, strict content policy, action audit, scrypt passwords, TOTP, SSO/OIDC, account disable, session idle timeout, before/after change audit, scoped API tokens, and HTTPS with HSTS (`DURIAN_TLS_CERT`) | None |
| 9 | Reports | On-demand and scheduled: alarm summary, shift report, trend tables | CSV export, per-point summary reports with watch-list and tag narrowing, and a daily scheduled email report (`durian/outputs.py`) | None |
| 10 | Calculation | Derived tags from expressions, simple sequences | Safe expression language over other points, as a `calc` source (`durian/calc.py`) | None |
| 11 | Resilience | Buffering, heartbeat or watchdog, comms-failure alarms | Write buffer, no-update detector, source health, source-down alarm, heartbeat and poll-duration overrun alarm (`durian/core.py`, `durian/app.py`) | None |
| 12 | Integration | REST, MQTT, webhooks, gateways | REST, MQTT TLS publisher and source, webhooks, HTTP poll, HTTP ingest push with scoped tokens, and a Sparkplug B payload codec (`durian/sparkplug_codec.py`) | A Sparkplug B source or publisher over a broker, OPC UA server |
| 13 | Diagnostics | Source and database health, system alarms | Source health, a database page in the console with health, retention and backups, and system alarms | None |

## Order of work, written 2026-10-20

Steps 1 to 6 have since been built: API tokens and inbound HTTP, data quality and source timestamps, the explicit alarm state model with shelving, suppression and KPIs, the tag fields and safe control, source-down alarms and heartbeat, and calculated points, reports and mimics. What remains from the baseline is the work in the gap column: scan classes, time-based write rate limits, historian compression, backfill and store-and-forward, a Sparkplug B interface over a broker, an OPC UA server, and the OPC UA, SNMP, BACnet and DNP3 drivers.

The historian work (row 5) and the migration layer it needed were already done when this note was written.
