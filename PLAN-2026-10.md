# DurianDB — orchestrator plan (2026-10-28)

Role split for this phase: the orchestrator (session model) only plans, finds gaps and verifies.
**Every code edit is executed by a DeepSeek subagent** (sonnet tier, ≤3 concurrent), under the
@ponytail ladder and @voltagent guardrails. The orchestrator alone commits and pushes, after
re-running the gate itself — an executor's "GREEN" is a claim, not a result.

## The loop (one feature = one turn of it)

1. **TEST FIRST.** DeepSeek writes the failing check before any implementation — a browser check,
   a `tests/test_*.py`, or a CI assertion, whichever proves the debt entry. The test is run and
   confirmed RED for the right reason before code is allowed to exist. This is deliberate:
   a test written after the code inherits the code's assumptions.
2. **CODE.** Same or second executor writes the minimum that turns it GREEN (ponytail ladder:
   reuse first, stdlib only, shortest diff, root cause not symptom).
3. **GATE.** Orchestrator runs it clean: `python tests/run_all.py`, `node tools/browser_ci.mjs <names>`
   as applicable. Never trusts the executor's transcript.
4. **COMMIT + PUSH** one feature per commit; delete the debt entry in the same commit it is fixed
   (TECHNICAL_DEBT.md §7). CI is GitHub Actions only.

## Guardrails every executor brief carries

- Ponytail: stdlib-first ladder; no unrequested abstraction; one runnable check per non-trivial change.
- Voltagent: trust-boundary validation stays; never weaken a test to pass it; never touch vendor
  `app/`, `app-en/`, `lab/` or read vendor jars; `.claude/` never committed; MariaDB on 3306 is the
  user's own — CI containers only.
- No commits by executors. Disjoint file sets between concurrent executors (port 9222 is single-tenant).
